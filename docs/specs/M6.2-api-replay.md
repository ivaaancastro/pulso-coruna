# M6.2 — API `/api/v1/replay`

- Estado: implementada
- Rama: `feat/M6.2-replay-api`
- Referencia: `docs/SPEC.md` (Contratos), `docs/ROADMAP.md` M6.2, `docs/specs/M4.1-api-snapshot-stream.md`, ADR-0024

## Problema y objetivo

El modo Reproducir (M6.3) necesita el histórico en el navegador sin que este toque la BD ni fuentes externas. Endpoint de solo lectura que devuelve una **ventana de ≤ 5 min** de una o varias capas, compacta (MessagePack, columnas), cacheable por CDN/navegador y con el **estado inicial** de cada entidad para poder arrancar a mitad de cualquier ventana.

## Alcance

Dentro: `GET /api/v1/replay`; esquema `ReplayWindowSchema` v1 en `packages/schema` (cambio de contrato, solo añade); lectura de brutos y de las vistas de 1 min (M6.1); caché HTTP + ETag + caché en memoria; límite por IP; tests; ADR-0024 (`@msgpack/msgpack`).

Fuera: cliente (M6.3: decodificar, buffer, precarga de la siguiente ventana, interpolación), URL compartible (M6.4), `pulse`, endpoint de «qué rango de fechas hay datos».

## Petición

`GET /api/v1/replay?from=<epoch ms UTC>&to=<epoch ms UTC>[&layers=bus,bike,…]`

- `from`, `to`: enteros decimales en **ms** (> 1e11: los segundos se rechazan). Ventana `[from, to)`.
- `0 < to − from ≤ 5 min`, `from ≤ ahora`, `from ≥ ahora − API_REPLAY_MAX_AGE_DAYS`. Si no, **400** `{error:"bad_request",message}`.
- `layers`: como en `snapshot` (`LayerIdSchema`; sin parámetro = todas; desconocidas o vacío → 400). Se ordenan en el orden canónico `LAYER_IDS`, así `layers=bike,bus` y `bus,bike` son la misma ventana (misma clave de caché y mismo ETag).
- **Alineación**: la web pide bloques con `from` múltiplo de 5 min (`from % 300000 == 0`) y `to = from + 300000`; solo esos reciben caché largo.

## Respuesta

`200`, `Content-Type: application/msgpack`, cuerpo = `ReplayWindow` codificado con MessagePack (`@msgpack/msgpack`, mapas con claves de texto). Decodificar y listo: `decode(new Uint8Array(await r.arrayBuffer()))`.

```
{ v: 1, from, to, resolution: "raw" | "1m",
  layers: { <layer>: ReplayLayer } }          // una entrada por cada capa pedida, aunque vacía
```

Todos los instantes de las series son **ms desde `from`** (`t = from + ts[i]`). `lon/lat` son enteros en 1e-5° (`lon = q / 100000`); `speed` entero en dm/s (`m/s = q / 10`); `heading` grados enteros 0–360. Constantes y conversores en `packages/schema/src/replay.ts` (`REPLAY_COORD_SCALE`, `REPLAY_SPEED_SCALE`, `fromReplayCoord`, `fromReplaySpeed`).

`ReplayLayer` según la capa (`kind`):

| capas                        | `kind`      | contenido             |
| ---------------------------- | ----------- | --------------------- |
| `bus`,`ship`,`plane`,`train` | `"mobile"`  | `tracks: Track[]`     |
| `bike`                       | `"station"` | `stations: Station[]` |
| `weather`,`air`,`sea`        | `"series"`  | `series: Series[]`    |

```
Track   = { id, meta?: {k: string|number}, init?: {dt, lon, lat, heading?, speed?},
            ts: int[], lon: int[], lat: int[], heading?: (int|null)[], speed?: (int|null)[] }
Station = { id, lon, lat, init?: {dt, bikes, docks}, ts: int[], bikes: int[], docks: int[] }
Series  = { stationId, metric, unit, init?: {dt, value}, ts: int[], value: number[] }
```

- **Columnas paralelas**: `ts`, `lon`, `lat` (y `heading`/`speed` si hay) tienen la misma longitud; `ts` estrictamente creciente, `0 ≤ ts[i] < to − from`. `heading`/`speed` solo existen si alguna muestra los tiene (`null` en las que no).
- **Estado inicial** (`init`): último valor conocido **antes de `from`**, dentro de `API_MAX_AGE_*_MS` (5 min móviles, 1 h bicis, 6 h observaciones; los mismos umbrales con que una lectura deja de contar como «viva»). `dt ≤ 0` es su edad respecto de `from`. Una entidad puede venir solo con `init` (sin muestras en la ventana); una sin `init` empieza a existir en `ts[0]`. Así el cliente puede arrancar en cualquier ventana sin la anterior: entre `init` y `ts[0]` interpola, tras la última muestra decide (extrapola o apaga según su política de vida útil).
- **`meta`** (línea del bus, nombre del barco…) se envía **una vez por entidad**: la de la última muestra de la ventana, o la del `init`. En `resolution: "1m"` no hay `meta` (la vista no la guarda; ver riesgos).
- `Station` lleva `lon/lat` una vez (fijos). `Series` identifica por `stationId` + `metric` (`observationKey`); la ubicación de la estación meteo/aire/mar la conoce el cliente por su catálogo/snapshot.
- Orden determinista (entidades por `id`, series por `stationId`,`metric`): mismos datos = mismos bytes = mismo ETag.
- **Resolución**: `raw` si `from ≥ ahora − API_REPLAY_RAW_DAYS` (28 días; margen sobre los 30 de retención, que borra por chunks de 1 día); si no, `1m`: una muestra por minuto y entidad (el último valor del minuto; `ts` = inicio del minuto), leída de las vistas `positions_1m`, `station_status_1m`, `observations_1m` de M6.1 (`apps/ingest/migrations/0002_retention.sql`). La decisión es por el `from` de la ventana; **no se mezclan** ambas en una respuesta (las vistas cubren todo lo anterior y los brutos solo duran 30 días, así que el solape de ≤ 5 min con el límite no pierde datos). El cliente trata las dos igual (solo cambia la densidad).

Ejemplo (bus con estado inicial, una estación y una serie; decodificado):

```
{ v:1, from:1760000100000, to:1760000400000, resolution:"raw",
  layers:{
    bus:{ kind:"mobile", tracks:[
      { id:"bus:1", meta:{line:"1A"},
        init:{ dt:-120000, lon:-840000, lat:4336000, heading:90, speed:50 },
        ts:[10000,25000], lon:[-841000,-841200], lat:[4337000,4337100],
        heading:[90,null], speed:[50,52] } ] },
    bike:{ kind:"station", stations:[
      { id:"st:1", lon:-840000, lat:4330000, init:{dt:-600000,bikes:2,docks:8},
        ts:[60000], bikes:[4], docks:[6] } ] },
    weather:{ kind:"series", series:[
      { stationId:"m1", metric:"wind_speed", unit:"m/s", init:{dt:-60000,value:3},
        ts:[], value:[] } ] } } }
```

## Caché y límites

- `Cache-Control` por ventana: incluye «ahora» (`to > now`) → `public, max-age=10`; pasada pero reciente (`to > now − 10 min`, la ingesta y el agregado de 1 min tardan en asentarse) o vacía → `public, max-age=60`; pasada, asentada y **alineada** → `public, max-age=86400, immutable` (`raw`; se recodificará a `1m` pasados 30 días) o `max-age=31536000, immutable` (`1m`); asentada no alineada → `max-age=3600`. (Un `no-store` no hace falta: 10 s protege la BD y la CDN lo respeta.)
- `ETag` fuerte (SHA-1 del cuerpo, 22 chars base64url); `If-None-Match` → **304** sin cuerpo.
- Caché en memoria (`API_REPLAY_CACHE_BYTES`, 32 MiB, LRU por bytes) solo de ventanas asentadas; consultas idénticas simultáneas comparten una sola lectura de BD.
- Límite por IP (reutiliza `ConnectionLimiter`): como máximo `API_REPLAY_MAX_PER_IP` (4) lecturas de BD simultáneas por IP → **429** `Retry-After: 2`. No cuentan los aciertos de caché, los 304 ni las peticiones inválidas. Es un límite de concurrencia, no de caudal; el caudal lo acota la caché (CDN, servidor y `immutable`). IP real con `API_TRUST_PROXY` (como el WS).
- Tamaño: `API_REPLAY_MAX_ROWS` (200 000 filas por tabla) y `API_REPLAY_MAX_BYTES` (4 MiB) → **413** `{error:"too_large"}` (pide menos capas). BD caída → **503** `Retry-After: 5`. Tablas inexistentes (ingesta sin migrar) → ventana vacía, no error.
- CORS y `X-Content-Type-Options` como el resto de la API.

## Configuración nueva

`API_REPLAY_MAX_AGE_DAYS` (365: las vistas de 1 min no tienen retención; si no hay datos de ese día, la ventana sale vacía), `API_REPLAY_RAW_DAYS` (28), `API_REPLAY_MAX_ROWS`, `API_REPLAY_MAX_BYTES`, `API_REPLAY_MAX_PER_IP`, `API_REPLAY_CACHE_BYTES`.

## Contrato (`packages/schema`)

Solo se **añade** `replay.ts` (`ReplayWindowSchema`, `REPLAY_VERSION = 1`, conversores): `Entity`, `StationStatus`, `Observation` y el mensaje WS no cambian, así que adaptadores, API y web siguen intactos. Validaciones: `v:1`, `to > from`, ≤ 5 min, tipo de payload correcto por capa, columnas de igual longitud, `ts` creciente y dentro de la ventana, cuantización entera. Cambios incompatibles → `v:2`.

## Criterios de aceptación

- [x] Ventana válida → MessagePack que valida con `ReplayWindowSchema`; round-trip `encode`/`decode`.
- [x] Ventanas > 5 min, capas inválidas, `from`/`to` mal formados o fuera de rango → 400 sin tocar la BD.
- [x] Estado inicial por entidad (con `meta` una vez) y capas pedidas siempre presentes.
- [x] `raw` para datos recientes y `1m` para antiguos (probado contra TimescaleDB real con las vistas de M6.1).
- [x] Cabeceras de caché por tipo de ventana, ETag/304, límite por IP, 413/503.

## Riesgos y decisiones

- `1m` pierde `meta` (la vista no la guarda): al reproducir días antiguos el cliente solo tendrá `id`. Mejora posible en M6.1: `last(meta, ts)` en `positions_1m`.
- Las vistas se materializan por política cada 5 min con `start_offset` de 3 días: un hueco mayor (ingesta o Timescale caídos más de 3 días) deja minutos sin agregar y, al borrarse los brutos, sin datos. Es una decisión de M6.1.
- Los agregados son `materialized_only` por defecto en TimescaleDB 2.x: los últimos ~6 min no están en la vista; no importa porque `1m` solo se usa pasados 28 días.
- Cuantizar a 1e-5° (~1 m) y 0,1 m/s está por debajo del ruido GPS/AIS y evita `float64` (9 B) en msgpack; el cliente debe dividir (`fromReplayCoord`).
- Límite por IP = concurrencia, no caudal: un scraper lento sigue siendo posible; lo acota la caché inmutable y, delante, la CDN. Si hiciera falta, un límite de caudal real sería otra tarea.
- Nueva dependencia: ADR-0024 (4,2 KB gzip el decodificador en la web, M6.3).
