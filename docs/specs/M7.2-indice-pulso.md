# M7.2 — Índice Pulso (`/api/v1/pulse`)

- Estado: implementada
- Rama: `feat/M7.2-pulso`
- Referencia: `docs/SPEC.md` (Contratos), `docs/ROADMAP.md` M7.2, `docs/specs/M6.2-api-replay.md`, ADR-0026

## Problema y objetivo

La web muestra un número «Pulso» ficticio. Hace falta un índice 0–100 calculado con los datos reales (50 = lo habitual para ese día-tipo y hora, 100 = muy por encima), servido por la API como serie temporal para el número grande y la serie del día (M7.3). Es honesto: marca `profile:"fixed"` mientras «lo habitual» sea una tabla estimada y no un perfil medido.

## Alcance

Dentro: `PulseSchema` v1 en `packages/schema` (solo se añade, `pulse.ts`); cálculo puro en `apps/api/src/pulse.ts`; lectura agregada en SQL (`pulse-db.ts`) de brutos + vistas de 1 min (M6.1); `GET /api/v1/pulse`; pesos en `PULSE_WEIGHTS`; ETag, `Cache-Control`, límite por IP; tests; ADR-0026.

Fuera: visualización y cliente (M7.3), perfil aprendido (solo el campo `profile` y el ADR), festivos, endpoint de rango con datos.

## Petición

`GET /api/v1/pulse?from=<epoch ms UTC>&to=<epoch ms UTC>[&step=<ms>]`

- `from`, `to`: enteros decimales en **ms** (> 1e11; los segundos se rechazan). `0 < to − from ≤ 24 h`; `from ≤ ahora` y `≥ ahora − API_REPLAY_MAX_AGE_DAYS`. `to` puede estar en el futuro (los tramos sin datos no dan puntos).
- `step`: ms, múltiplo de 60 000 entre 60 000 y 3 600 000 (defecto 300 000). Tramo k = `[from + k·step, from + (k+1)·step)`.
- Inválido → **400** `{error:"bad_request",message}` sin tocar la BD.

## Respuesta

`200 application/json` = `Pulse` (JSON, no MessagePack):

```
{ v:1, from, to, stepMs, profile:"fixed"|"learned",
  points:[{ ts, value, layers:{ <layer>: number } }] }
```

- `ts` = inicio del tramo (`from + k·stepMs`), estrictamente creciente; solo hay punto si algún tramo tiene datos de alguna capa. `value` 0–100 con 1 decimal. `layers[x]` = razón relativa de la capa (1 = habitual, 0 = nada, tope 3, 2 decimales); solo capas con datos en el tramo.
- Validación zod estricta (`PulseSchema`): `v:1`, ventana ≤ 24 h, paso válido, `ts` alineado y dentro de la ventana, claves desconocidas rechazadas.

## Fórmula

Capas que entran: `bus, bike, ship, plane, weather, sea, air` (`train` no tiene fuente). Para cada tramo y capa se obtiene una razón `r` (1 = lo habitual) acotada a `[0, 3]`:

| capas                 | actividad observada                                                                                | lo habitual                                        | razón                                           |
| --------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ----------------------------------------------- |
| `bus`,`ship`,`plane`  | nº de entidades **distintas en movimiento** en el tramo (velocidad ≥ 0,5 m/s o desconocida)        | `pico × forma[día-tipo][hora]`                     | `(obs + 1) / (habitual + 1)`                    |
| `bike`                | rotación: `Σ \|Δ bicis\|` entre lecturas consecutivas de cada estación (hueco ≤ 15 min), por 5 min | idem                                               | idem                                            |
| `weather`,`air`,`sea` | media por métrica conocida; desviación `(valor − normal)/escala` acotada a ±2                      | tabla `OBSERVATION_NORMALS` (viento, pm10, marea…) | `1 + 0,25 · media de desviaciones` ∈ [0,5; 1,5] |

- **Perfil fijo** (`FIXED_PROFILE`): `pico` estimado (bus 40, bici 25 cambios/5 min, barcos 6, aviones 3) × `forma` (fracción del pico de un laborable) por **laborable / sábado / domingo** y hora local 0–23. Día-tipo y hora se calculan en `Europe/Madrid` del inicio del tramo (`Intl`, con horario de verano); internamente todo es UTC. Sin festivos. Barcos y aviones usan una forma más plana que bus/bici.
- **Suavizado +1** en numerador y denominador: de madrugada «lo habitual» es ~0 y sin él una sola entidad dispararía el cociente.
- **Capa sin datos ≠ actividad 0**: una capa móvil o de bicis sin ninguna lectura en toda la ventana se omite; con lecturas en la ventana pero no en el tramo cuenta 0 en movimiento (de noche no hay buses, y eso es información). Las ambientales se omiten en tramos sin lectura.
- **Tramo en curso** (o recortado por `to`): la rotación de bicis se extrapola al tramo completo (`rot · 5 min / transcurrido`; no se extrapola con < 1 min transcurrido). No se calculan tramos con inicio ≥ ahora.
- **Media ponderada**: `value = clamp(50 · Σ wᵢ·rᵢ / Σ wᵢ, 0, 100)` sobre las capas presentes, redondeado a 1 decimal. 50 = normal; ≥ 2× lo habitual = 100; sin actividad ≈ 0. Las capas ambientales, por su rango ±0,5 y peso bajo, mueven el índice unos pocos puntos como máximo.

## Pesos (configuración)

`PULSE_WEIGHTS`: JSON parcial `{"bus":1.5,"sea":0}` sobre los defectos `bus 1, bike 1, ship 0.4, plane 0.4, weather 0.3, air 0.3, sea 0.2`. Capas desconocidas, pesos negativos / no numéricos / > 100, JSON roto o todo a 0 → la API no arranca (error claro). Peso 0 desactiva la capa (ni se lee). También: `API_PULSE_MAX_PER_IP` (2) y `API_PULSE_MAX_GLOBAL` (2). Ver `.env.example`.

## Datos

`DataSource.pulse(q)` → `readPulseAggregates` agrega en SQL (no se traen filas; las salidas son del orden de tramos × capas): `positions`/`station_status`/`observations` con `ts >= corte` `UNION ALL` `positions_1m`/`station_status_1m`/`observations_1m` con `bucket < corte` (`corte` = `replayCutoff`, 30 días, igual que replay). Sin vistas → solo brutos; sin tablas → vacío (respuesta `points:[]`).

## Caché y límites

- `Cache-Control`: la ventana incluye «ahora» → `public, max-age=30`; reciente (`to > ahora − 10 min`) o sin puntos → `max-age=60`; pasada y asentada → `max-age=3600` (no `immutable`: el perfil fijo se sustituirá). Errores: `no-store`.
- `ETag` fuerte (SHA-1 del cuerpo); `If-None-Match` → **304**.
- Límite por IP (`ConnectionLimiter`): ≤ `API_PULSE_MAX_PER_IP` lecturas de BD simultáneas por IP y `API_PULSE_MAX_GLOBAL` en total → **429** `Retry-After: 2`. Consultas idénticas simultáneas comparten una sola lectura. BD caída → **503** `Retry-After: 5`.

## Contrato (`packages/schema`)

Solo se **añade** `pulse.ts` (`PulseSchema`, `PULSE_VERSION = 1`, constantes de ventana/paso). `Entity`, `StationStatus`, `Observation`, WS y `ReplayWindow` no cambian: adaptadores, API y web siguen intactos. Cambios incompatibles → `v:2`.

- [x] Respuesta válida contra `PulseSchema` (ts alineados, value 0–100 con 1 decimal, capas 0..3, `profile:"fixed"`).
- [x] Validación estricta de `from`/`to`/`step` (ventana ≤ 24 h, segundos rechazados, paso múltiplo de 1 min) → 400 sin tocar la BD.
- [x] Cálculo puro: lo habitual = 50, ≥ 2× = 100, sin actividad ≈ 0; pesos configurables y validados; ambientales acotadas; capa sin datos omitida; día-tipo/hora en Madrid con horario de verano.

- [x] ETag/304, `Cache-Control` por frescura, 429 por IP y global, 503.

## Riesgos y decisiones

- El perfil fijo es una estimación: el nivel absoluto del índice (¿40 o 60 un martes normal?) no está calibrado; la forma diaria sí es plausible. Hasta tener un mes de histórico, la UI debe etiquetar «perfil fijo». Ver ADR-0026 para el perfil aprendido.
- Con ≤ 30 días la resolución es la de las muestras brutas (~15 s); en datos antiguos (`1m`) la rotación de bicis sale algo menor (se pierden cambios que se compensan dentro del minuto).
- Un festivo se compara con un laborable.
- «Sin datos de la capa en toda la ventana» no distingue ingesta caída de servicio nulo (p. ej. una ventana entera de madrugada sin buses): esa capa no cuenta y el resto renormaliza. Con ventanas de horas es raro; M7.3 puede pedir ventanas de varias horas.
- Cada petición agrega hasta 24 h en la BD: protegida por `statement_timeout`, límites por IP/global y la caché HTTP (CDN).
