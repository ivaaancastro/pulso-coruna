# M4.1 — API snapshot, stream y health

- Estado: implementada
- Rama: `feat/M4.1-api-stream`
- Referencia: `docs/SPEC.md` (Contratos), `docs/ROADMAP.md` M4.1

## Problema y objetivo

La ingesta (M3.5) graba en TimescaleDB, pero el navegador solo puede hablar con nuestra API. Hace falta un servidor `apps/api` (`@pulso/api`, Fastify) que lea lo grabado y lo sirva cumpliendo el contrato de `packages/schema`: foto actual, flujo en vivo y estado de las fuentes.

## Alcance

Dentro: `GET /api/v1/snapshot`, `WS /api/v1/stream`, `GET /api/v1/health`; límite de conexiones WS por IP; CORS; imagen Docker, servicio en compose y proxy en Caddy; tests; ADR-0018 (dependencias) y ADR-0019 (mecanismo del stream).

Fuera: `replay` y `pulse` (M6/M7), cliente WS (M4.2), autenticación, límite de peticiones HTTP (lo hace el proxy si hace falta), modificar `packages/schema`, migraciones (las aplica la ingesta; la API solo lee).

## Diseño

- **Lectura** (`db.ts`): último estado por clave con `DISTINCT ON` sobre ventanas de antigüedad configurables (por defecto 5 min móviles, 1 h estaciones de bici, 6 h observaciones). Una fila más vieja que la ventana deja de existir en la foto (para móviles equivale a un `remove`). Las consultas concurrentes se unen y el resultado se cachea `API_SNAPSHOT_CACHE_MS` (1 s). Si las tablas aún no existen (la ingesta no ha migrado) o están vacías: listas vacías, nunca error. Si la BD no responde: 503 (HTTP) o cierre WS 1013.
- **Snapshot**: `?layers=bus,bike` (sin parámetro, todas). Capas desconocidas o lista vacía → 400 `{error:"bad_request",message}`. Respuesta = `SnapshotMessage` con solo las capas pedidas, todas presentes aunque vacías.
- **Stream** (ADR-0019): sondeo de la BD cada `API_POLL_MS` (2 s) **solo mientras hay clientes**, diff en memoria por capa (`diff.ts`: clave `id` u `observationKey`; igualdad por contenido serializado), un `delta` por capa con cambios. El snapshot inicial sale del mismo estado en memoria en el mismo turno en que se registra el cliente → ni se pierden ni se repiten cambios. `?layers=` opcional también en el WS (400 antes del handshake si es inválido).
- **Límites y limpieza**: máximo `API_WS_MAX_PER_IP` (10) conexiones simultáneas por IP; rechazo previo al handshake con **429** + `Retry-After` (y recomprobación al aceptar → cierre 1008). La IP real viene de `X-Forwarded-For` solo con `API_TRUST_PROXY=true` (compose lo activa). Ping cada `API_WS_PING_MS` (30 s): quien no contesta pong en un ciclo se termina y libera su hueco. Cliente con más de `API_WS_MAX_BUFFERED_BYTES` (4 MiB) pendientes → desconectado (reconectará y recibirá un snapshot). Mensajes entrantes ignorados (`maxPayload` 1 KiB).
- **Health**: `{v:1, ts, status, db:{ok,latencyMs}, sources:[{id,status,reportedStatus,intervalMs,lastSuccessAt,ageMs,lastErrorAt,consecutiveFailures}], layers:{<layer>:{lastDataAt,ageMs}}}`. `status` efectivo por fuente = peor entre lo anotado por la ingesta y la edad de la última lectura (`degraded` pasado 3× el intervalo, `down` pasado 9×): si la ingesta muere, `source_health` se queda en `ok` y la API lo corrige. `layers` (última marca por capa en 24 h, `null` = sin datos) alimenta la etiqueta «sin datos desde hace X min» sin que el cliente conozca el mapa fuente→capa. No se publica `last_error` (puede contener URLs). BD caída → 503 con `status:"down"`. Caché 5 s.
- **CORS**: `API_CORS_ORIGINS` (por defecto `*`: datos públicos, solo `GET`, sin cookies). Si es una lista, también se exige en el handshake WS (403). En producción la web y la API comparten dominio vía Caddy, así que no hace falta CORS.
- **Empaquetado**: esbuild a un `dist/main.js` (ADR-0017; banner `createRequire` porque Fastify usa `require`), `Dockerfile.api` multietapa, usuario `node`, `HEALTHCHECK` contra `/api/v1/health`. Compose: servicio `api` sin puertos publicados, tras `db` sano e `ingest` arrancado. Caddy: `handle /api/*` → `reverse_proxy api:3000` (WebSocket incluido).

## Criterios de aceptación

- [x] `GET /api/v1/snapshot?layers=bike,weather` valida con `SnapshotMessageSchema`; capas desconocidas → 400.
- [x] `WS /api/v1/stream` envía snapshot al conectar y luego `delta` (`v:1`) con upserts y removes por clave de identidad (observaciones por `observationKey`).
- [x] Límite de conexiones WS por IP configurable (429 / cierre 1008), ping/pong y limpieza de clientes caídos.
- [x] `GET /api/v1/health`: estado por fuente (ok/degraded/down), última lectura, edad y estado de la BD.
- [x] Capas sin datos → listas vacías (bus sin iTranvías); CORS y cabeceras razonables; sin llamadas a terceros.
- [x] Tests Vitest: diff/deltas, esquemas, hub, app con WS reales y BD efímera (se saltan con `PULSO_TEST_DB=skip`).
- [x] `Dockerfile.api`, servicio en compose, proxy `/api/*` en Caddy, `docs/deploy.md` y `.env.example`.

## Riesgos y decisiones

- Sondeo = retraso de hasta `API_POLL_MS` (2 s) respecto a la grabación y coste constante de ~3 consultas cada 2 s mientras haya algún cliente (ADR-0019).
- Un móvil que lleva más de `maxAgeMs` sin datos desaparece del mapa; si una fuente cae, sus capas se vacían tras la ventana (la web usa `health.layers` para explicarlo, M4.6). Las ventanas son configurables.
- Sin límite HTTP por IP en la API: un martilleo de `snapshot` queda acotado por la caché de 1 s y consultas unidas, no por IP.
- `API_TRUST_PROXY=true` fuera de un proxy permitiría falsear la IP con `X-Forwarded-For`; por eso el defecto es `false` y solo compose lo activa.
- Dependencias nuevas: ADR-0018. Contrato (`packages/schema`) sin cambios.
